# 私活接单参谋

把模糊需求变成一份可以决策、报价和继续沟通的接单结论。目标不是替用户盲目接单，而是尽快回答三个问题：客户到底要什么、最小验证怎么做、这单是否值得接。

## 工作流

### 1. 整理输入

- 阅读客户聊天、截图、附件和已有回复，按时间顺序还原对话。
- 默认隐去姓名、手机号、账号、店铺名、链接参数等可识别信息。
- 将内容拆成 `已确认事实`、`合理推断`、`未知信息`，不得把推断写成客户承诺。
- 需要结构化记录时，使用 [references/intake-schema.md](references/intake-schema.md)。

### 2. 用一句话复述需求

采用“输入 -> 处理 -> 输出 -> 使用者”的格式，例如：

> 读取货盘表和同行链接，生成待确认价格，再在一个已登录店铺中完成少量商品上架并输出操作记录。

如果一句话无法说清，说明范围尚未收敛，先补问而不是报价。

### 3. 找出阻塞问题

只问会改变技术方案、工期、价格或验收结果的问题，通常不超过 5 个。优先确认：

1. 实际操作流程和输入样例；
2. 账号、平台、数量和频率；
3. 数据是否在网页上真实可见，是否有官方接口；
4. 成功标准、失败处理和人工介入方式；
5. 部署、维护和页面改版后的责任边界。

### 4. 评估风险与可行性

- 按 [references/risk-rules.md](references/risk-rules.md) 检查平台限制、隐藏数据、账号、隐私、知识产权和交付风险。
- 登录状态可用不等于自动化稳定；网页能看到不等于脚本能合法、持续获取。
- 对验证码、风控、移动端专属内容、直播价、新客券、平台补贴、私有接口等，不承诺绕过。
- 可运行 `python scripts/score_request.py request.json` 生成一致的评分和建议；评分是讨论辅助，不替代实际验证。

### 5. 划定最小验证

把售前演示、付费验证和正式产品分开：

- `售前演示`：使用假数据或模拟页面，证明交互和产品表达，不证明真实平台已打通。
- `付费验证`：用 1 个账号、3-5 条真实数据跑通关键链路，允许人工处理验证码，输出成功与失败记录。
- `正式产品`：在验证通过后再按真实数量、并发、账号和维护要求报价。

遇到高风险平台自动化、隐藏数据或多账号操作时，不直接报完整批量版固定价。

### 6. 估算与回复

- 报价以范围、假设和验收条件为前提，优先给区间或分阶段报价。
- 工期包含开发、联调和一次验收修正；注明客户资料延迟不计入工期。
- 回复使用自然中文，短句为主，不堆术语，不表现得像模板生成。
- 未掌握市场行情时，将金额标为“当前评估基线”，不要伪装成行业统一价。

## 输出格式

按需输出以下内容，避免为了完整而冗长：

```markdown
## 接单结论
- 建议：可详细报价 / 先补信息 / 只接付费验证 / 不建议承接
- 一句话需求：...
- 核心原因：...

## 已确认与未知
- 已确认：...
- 需要确认：...

## MVP 边界
- 包含：...
- 不包含：...
- 验收：...

## 工期与报价
- 当前评估：...
- 前提：...

## 风险
- 风险 -> 影响 -> 应对

## 可直接发送的回复
...
```

## 决策底线

- 客户目标依赖不可见或不可验证的数据：先做数据可得性验证。
- 客户拒绝提供样例、操作录屏或验收标准：不报正式固定价。
- 需求涉及批量账号操作或平台风控：限定账号和频率，保留人工检查点。
- 演示使用模拟数据时：明确标注 Demo，不暗示真实后台已接通。
- 不为获得订单隐藏关键风险，也不替客户执行违规绕过。
